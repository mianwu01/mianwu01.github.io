一现象

退化是真实的，但很局部、且未达统计显著

核心原因不是「SE 普遍破坏了 Dev 能力」，而是当前这套 SE-SFT 配方会轻微收缩模型的长尾覆盖：正确概率更集中到一部分题上，因此 pass@1 可以持平甚至上升，但原本只有小概率能解出的边界题变成 0/16，导致 pass@16 和 solved 下降。

二成因

当前 SE-SFT 配方的五个结构性问题

2.1SFT 优化目标和 pass@16 不一致

当前 K1 SFT 每题主要模仿一条被筛选出的正确答案。交叉熵目标只要求提高这条轨迹的似然，并不奖励：

  • 保留 Base 的其他算法模式；
  • 16 次采样覆盖不同解法；
  • 保留某道题原本只有 1/16 的稀有成功模式。

拒绝采样选出的答案确实更好，但「答案质量更高」不等于「学生的解法分布更广」。

2.2训练没有直接监督自主 thinking

这些 native-final 模型使用 loss_scope = final：原生 assistant.thinking 出现在 teacher-forced 上下文中，但 thinking token 被 mask。也就是说，模型训练时是在正确思考轨迹之后学习输出 final，却没有被直接训练如何自主生成这条思考轨迹。

训练 prompt 正确的 assistant.thinkingteacher-forced · token 被 mask，无 loss final唯一计算 loss 的部分
测试 prompt 自己生成的 thinking往往更短、分布不同 final照常自信输出

测试时模型必须自己生成 analysis，于是容易出现「训练：正确 thinking → 学习正确 final；测试：自己产生较短/不同的 thinking → 自信地产生 final」。这也解释了为什么 SFT 常常改善代码格式，却未必改善推理覆盖。

2.4三个「不同 SE」其实共享同一种训练缺陷

它们并不是三种独立方法：

  • 标准 SE 和 hp778 使用同一套 se_k1_native_final 数据与 final-only loss，只改变剂量和超参数。
  • bucket-0 refit 使用其中 794 条 bucket-0 子集，仍然是 final-only loss。
  • K1 每题只有一条目标轨迹。
  • SE evolution 输出的格式并不统一，很多 loop≥1 样本是较短、偏代码式 final。

因此超参数只能减轻遗忘，不能修复目标函数和数据格式的共同问题。

2.5训练剂量确实存在遗忘趋势

我的判断 SE-SFT 在 bucket-0 上产生了真实的 hard-capability 改善，但以轻微的 Dev 长尾覆盖收缩为代价。这个代价集中于最难的 Dev 1–3，并且单个正式对照尚未达到统计显著；它更像 SFT 的概率集中、CoT 缩短和少量遗忘，而不是整体 coding 能力下降。

真正的修复重点不是继续寻找普通 LR/BS，而是：

  • 统一并语义校验 analysis/final 格式；
  • 直接监督干净的原生 thinking，而不是只训 final；
  • 混入一定比例的 Base-compatible replay；
  • 按题归一化并选择算法 family 多样的 SE 解，而不是同一 breakthrough 的 descendants；
  • 使用真正达到相同 thinking budget 的 harness；
  • 如果做 RL，必须加入对 Base 的 KL/retention 约束，否则 GRPO 也可能进一步 mode collapse。
其中统一格式仍需要先通过 human semantic gate：canonical v1 的前 12 条中有 3 条实质矛盾，暂时不能直接拿去训练。
三澄清

bucket-0 改善与 Dev 1–3 丢题并不矛盾

「bucket-0 明明更难，为什么它能改善、Dev 1–3 却丢题」这个困惑很合理，但有两个关键前提需要修正：

  1. bucket-0 不等于在一条单调难度轴上「严格比 1–3 更难」。
  2. 换成 Base floor=0 后，bucket-0 refit 在 Dev 1–3 上其实没有退化，反而略有改善。

3.2为什么 bucket-0 不一定是同一种「更难」

bucket 是根据 Base 在最初 16 次采样中解出多少次划分的，不是根据算法复杂度划分的：bucket-0 表示观测到 0/16，bucket 1–3 表示观测到 1–3/16。这是一个带有很大采样噪声的观测。比如一道真实单次成功率为 5% 的题，16 次全部失败的概率仍有：

(1 − 0.05)16 ≈ 44%

所以它很可能被分进 bucket-0；另一次采样又可能进入 1–3。bucket-0 同时混合了：

  • 真正极难的问题；
  • Base 的系统性盲点；
  • 本来有低成功率、但恰好 16 次全失败的问题；
  • SE 特别擅长搜索到某类修复方案的问题。

而 Dev 1–3 可能包含完全不同的算法 family。代码题难度不是一个可以线性迁移的标量：学会一批极难 DP 的解法，不保证保留另一批中等难度 parsing / graph / implementation 的稀有解法模式。

3.3「训练集中有 1–3 的答案」为什么还不够

训练集确实有 745 条 bucket 1–3 数据，但不是 Dev 中这 50 道原题——Dev IDs 与训练集严格隔离，否则就是测试泄漏。更重要的是，训练信号的性质非常不同：

训练 slice总行数真正 only-SE 行数only-SE 占比

  • bucket-0 数据中约四成代表「SE 找到了常规搜索没有找到的新能力信号」。
  • 1–3 的 745 条答案里，真正代表 SE 新 reach 的只有约 25 条。
  • 其余大多是 Base/independent 本来就能解的题，只是再提供一条正确答案。

所以 bucket-0-only 训练非常富集 SE 特异信号；而 1–3 训练数据更多是对已知能力的答案 replay。拥有正确答案，不等于它提供了新的、可迁移的推理技能。此外，当前是 K1 + final-only loss：每题主要只有一条正确轨迹；thinking 不直接计算 loss；训练目标不要求保留其他解法；也不直接优化 pass@16 的算法覆盖。因此模型可以提高某些 1–3 问题的成功概率——表现为 pass@1 上升——同时消除另一些题原本只有 1/16 左右的稀有成功模式。

五修复方案

family-balanced · insight-first · per-problem-normalized 的多解蒸馏

最可行的办法不是把 SE 的 K4 全部塞进 SFT。目标不是让模型记住更多代码，而是先学习

p(algorithm family | problem)

然后再学习

p(reasoning, code | problem, algorithm family)

5.1为什么现有 K4 没把多样性蒸馏进去

  • 多个答案经常是同一次 breakthrough 的 descendants：AST 不同但算法相同。
  • 某题有 4 条就获得 4 倍梯度权重，改变了题目剂量。
  • SE loop-0、loop≥1、BoN 的 analysis/final 格式不统一。
  • native-final 只训练 final，真正不同的 thinking 没有直接 loss。

因此模型看到的常常不是「四种算法」，而是「同一种算法的四种代码写法」。

5.2建议的数据流水线

① 先识别真正的 algorithm family。不能只用文本去重或者 AST2。每个候选至少提取：核心 observation、算法类别、状态定义、关键不变量、数据结构、时间和空间复杂度、与其他候选的实质差异、SE lineage / breakthrough loop / parent。聚类时结合规范化 AST/CFG、数据结构和复杂度、LLM 提取的 algorithm descriptor、lineage 信息、pairwise semantic-family classifier。

② 每个 family 只保留一个代表。对每道题取 K_i = min(4, 真实 algorithm families 数)，不要为了凑 K4 填入重复 descendants。例如一题可能保留：排序 + greedy、prefix/suffix、binary search、dynamic programming。如果一题只有一种真实算法，就只保留 K1。训练行数可以不同，但题目总权重不能不同。

③ 每题总梯度权重固定。如果一道题有 Fi 个 family，则每条 family 样本权重为：

wij = 1 / Fi　　（K1 题：每条权重 1；K2 题：1/2；K4 题：1/4）

或者每个 epoch 每题随机采一个 family，下一 epoch 换另一个。这样可以学习多解，而不会让多解题获得 4 倍训练剂量。这是现有 naive K4 最重要的控制变量。

5.3用 insight 作为「多模态入口」

统一后的 analysis 不应该只是很短的答案摘要，而应让不同算法从一开始就分叉：

INSIGHT
最关键、非显然的观察是什么？为什么这个观察把原问题转化为可解形式？
APPROACH
使用什么算法和数据结构？状态/变量的含义是什么？按什么顺序计算？
CORRECTNESS
核心不变量是什么？为什么不会漏解或重复？
COMPLEXITY
时间复杂度、空间复杂度。
IMPLEMENTATION CHECKS
边界条件、容易出错的细节。
FINAL
固定为一致格式的完整 Python 解答。

这样一题的四种 family 会在最早的 Insight token 上分叉，模型比较容易保留多模态分布。否则四份相似长代码做普通 MLE，很容易被平均成一个主模式。

注意 canonical 数据的风险：不能直接使用当前 canonical v1——人工 gate 的前 12 条中有 3 条实质矛盾。更安全的生成流程是：① 先让 teacher 只看问题，提出若干可能 insight；② 将 insight 与 verified SE code family 对齐；③ critic 检查 insight、算法、复杂度和代码是否一致；④ repair；⑤ 再跑代码测试和人工语义抽检。不要直接让 teacher 看着答案编一段很长的「伪原生 CoT」——此前 regen/full 已证明这种 answer-conditioned explanation 容易短化推理并造成能力遗忘。

5.4训练目标分三阶段调整

第一阶段：低风险、立即可做。先保持当前 native-final + final-only，只改变解法选择：

如果 C 明显优于 A/B，说明过去 K4 失败主要是重复 descendants 和剂量失控，不必先引入格式变量。

第二阶段：蒸馏 reasoning diversity。语义 gate 通过后增加：

这样能把「family selection」和「reasoning supervision」分开诊断。

第三阶段：两段式生成。推理时不要立即生成完整代码：

5.5数据混合建议

不建议所有 bucket 都只用 SE：

BUCKET-0优先 SE，尤其 strict only-SE 和真正不同的 breakthrough family。
BUCKET 1–3SE 与 BoN/independent 合并后按 family 选择。
BUCKET 4–15优先 Base-compatible BoN/loop-0 replay：这些 bucket 中 independent 的真实算法 family 反而更多。
全程保留 20%–30% 的 Base-compatible replay，防止 Dev coverage 收缩。

可以概括为：bucket-0 = SE discovery；1–3 = SE + BoN family union；4–15 = BoN/loop-0 retention replay。

5.6如果以后使用 GRPO

GRPO 不能只奖励 correctness，否则也会收缩到单一高奖励模式。至少需要：

R = Rcorrect + λ·Rfamily novelty − β·KL(π ‖ πbase) − γ·Rduplicate

每组生成 8–16 个候选：完整测试通过获得 correctness reward；与组内其他正确答案属于新 family，获得 novelty reward；同 family 重复不给额外奖励；用 KL 保留 Base 的 Dev 分布；对长度和格式加约束。

但我会先做 family-balanced SFT：它更便宜，也能直接判断 SE 的多样性究竟有没有训练价值。如果这一步都没有收益，直接做 GRPO 很可能只是更昂贵的 mode collapse。

最关键的实验 不是「K1 vs K4」，而是：K1 vs naive K4 vs genuine-family-balanced K≤4——在相同题目权重、相同 token/update 剂量和相同格式下比较。这才能真正回答 SE 的丰富解法能否被蒸馏。
