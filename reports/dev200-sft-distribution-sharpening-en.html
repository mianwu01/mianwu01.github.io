ISymptom

The regression is real, but local — and not statistically significant

The root cause is not that "SE broadly damages Dev ability." Rather, the current SE-SFT recipe slightly contracts the model's long-tail coverage: correct-answer probability concentrates onto a subset of problems, so pass@1 can hold or even rise, while borderline problems that used to be solved with small probability drop to 0/16 — pulling pass@16 and solved down.

IICauses

Five structural flaws in the current SE-SFT recipe

2.1The SFT objective is misaligned with pass@16

Current K1 SFT imitates mostly one filtered correct answer per problem. The cross-entropy objective only asks to raise that trajectory's likelihood; it does not reward:

  • preserving Base's other algorithmic modes;
  • covering different solutions across 16 samples;
  • keeping a problem's rare 1-in-16 success mode alive.

Rejection sampling does pick better answers — but "higher answer quality" is not "a wider solution distribution in the student."

2.2Autonomous thinking is never directly supervised

These native-final models use loss_scope = final: the native assistant.thinking appears in the teacher-forced context, but its tokens are masked. That is, the model learns to emit the final after a correct reasoning trace — it is never directly trained to generate that trace on its own.

Train prompt correct assistant.thinkingteacher-forced · tokens masked, no loss finalthe only part with loss
Test prompt self-generated thinkingoften shorter, differently distributed finalemitted just as confidently

At test time the model must produce its own analysis, so we get: train on "correct thinking → learn the correct final," test on "shorter / different thinking → confidently emit a final." This also explains why SFT often improves code formatting without improving reasoning coverage.

The same floor=7300 label is therefore not the same actual thinking budget. Standard SE / hp778 think about 14% less than Base on average — likely a further hit to the hardest Dev 1–3.

2.4The three "different SEs" share one training flaw

They are not three independent methods:

  • Standard SE and hp778 use the same se_k1_native_final data and final-only loss, varying only dose and hyperparameters.
  • The bucket-0 refit uses its 794-row bucket-0 subset — still final-only loss.
  • K1 gives each problem only one target trajectory.
  • SE evolution outputs are not format-consistent; many loop≥1 samples are shorter, code-heavy finals.

So hyperparameters can only soften the forgetting — they cannot fix the shared objective and data-format problems.

2.5Training dose does drive forgetting

My read SE-SFT produces a real hard-capability gain on bucket-0, at the cost of a slight contraction of Dev long-tail coverage. The cost concentrates in the hardest Dev 1–3, and no single formal comparison reaches statistical significance. It looks like SFT's probability concentration, CoT shortening, and mild forgetting — not an across-the-board decline in coding ability.

The real fixes are not more LR/BS search, but:

  • Unify and semantically validate the analysis/final format;
  • Directly supervise clean native thinking, not just the final;
  • Mix in a share of Base-compatible replay;
  • Normalize per problem and pick algorithm-family-diverse SE solutions, not descendants of one breakthrough;
  • Use a harness that actually reaches the same thinking budget;
  • For RL, add a KL / retention constraint toward Base — otherwise GRPO can mode-collapse further.
Unifying the format must first pass a human semantic gate: 3 of the first 12 canonical v1 items are substantively contradictory and cannot be used for training yet.
IIIClarification

The bucket-0 gain and the Dev 1–3 losses are not contradictory

The confusion — "bucket-0 is supposedly harder, so how can it improve while Dev 1–3 loses problems?" — is reasonable, but two premises need correcting:

  1. bucket-0 is not "strictly harder than Dev 1–3" on one monotonic difficulty axis.
  2. Against Base floor=0, the bucket-0 refit does not regress on Dev 1–3 — it improves slightly.

3.2Why bucket-0 is not the same kind of "harder"

Buckets are assigned by how many of Base's initial 16 samples solved a problem — not by algorithmic complexity. bucket-0 means an observed 0/16; bucket 1–3 means an observed 1–3/16. That observation carries heavy sampling noise: a problem with a true 5% per-sample success rate still fails all 16 with probability

(1 − 0.05)16 ≈ 44%

— so it may well land in bucket-0 on one run and in 1–3 on another. bucket-0 therefore mixes:

  • genuinely extremely hard problems;
  • Base's systematic blind spots;
  • low-but-nonzero success-rate problems that happened to go 0-for-16;
  • problems where SE is especially good at searching out a class of fixes.

Dev 1–3 may contain entirely different algorithm families. Coding-problem difficulty is not a linearly transferable scalar: mastering a batch of very hard DP solutions does not guarantee keeping the rare solution modes of mid-difficulty parsing / graph / implementation problems.

3.3Why "the training set has bucket 1–3 answers" is not enough

The training set does hold 745 bucket 1–3 rows — but not these 50 Dev problems: Dev IDs are strictly held out from training; anything else would be test leakage. More importantly, the nature of the training signal differs sharply:

Training sliceTotal rowsStrict only-SE rowsonly-SE share
bucket-079432340.7%

  • About 40% of the bucket-0 data represents "SE found a capability signal that ordinary search did not."
  • Of the 745 bucket 1–3 answers, only about 25 represent genuinely new SE reach.
  • The rest are mostly problems Base/independent could already solve — just one more correct answer.

So bucket-0-only training is strongly enriched in SE-specific signal, while bucket 1–3 data is mostly answer replay of known capability. Having a correct answer does not mean it provides a new, transferable reasoning skill. On top of that, the current setup is K1 + final-only loss: mostly one correct trajectory per problem; thinking carries no direct loss; the objective neither asks to preserve alternative solutions nor optimizes pass@16's algorithmic coverage. The model can therefore raise success probability on some 1–3 problems — visible as higher pass@1 — while erasing other problems' rare, roughly 1-in-16 success modes.

VThe fix

Family-balanced, insight-first, per-problem-normalized multi-solution distillation

The most viable path is not stuffing all of SE's K4 into SFT. The goal is not for the model to memorize more code, but to first learn

p(algorithm family | problem)

and then

p(reasoning, code | problem, algorithm family)

5.1Why the existing K4 did not distill diversity

  • Multiple answers are often descendants of the same breakthrough — different ASTs, same algorithm.
  • A problem with 4 rows gets 4× gradient weight, changing per-problem dose.
  • SE loop-0, loop≥1 and BoN analysis/final formats are inconsistent.
  • native-final trains only the final — genuinely different thinking gets no direct loss.

So the model often sees not "four algorithms" but "four ways of writing the same algorithm."

5.2Proposed data pipeline

① Identify true algorithm families first. Text dedup or AST2 alone is not enough. Extract from each candidate at least: the core observation, algorithm class, state definition, key invariants, data structures, time and space complexity, its substantive difference from other candidates, and its SE lineage / breakthrough loop / parent. Cluster using normalized AST/CFG, data structures and complexity, an LLM-extracted algorithm descriptor, lineage information, and a pairwise semantic-family classifier.

② Keep one representative per family. For each problem take K_i = min(4, true algorithm family count); never pad to K4 with duplicate descendants. A problem might keep, say: sorting + greedy, prefix/suffix, binary search, and dynamic programming. If a problem has only one true algorithm, keep K1. Training row counts may differ; per-problem total weight must not.

③ Fix the per-problem gradient weight. If a problem has Fi families, each family sample gets:

wij = 1 / Fi   (K1 problems: weight 1 each; K2: 1/2; K4: 1/4)

Or sample one family per problem per epoch, rotating each epoch. Either way the model learns multiple solutions without multi-solution problems getting 4× the training dose. This is the single most important control missing from naive K4.

5.3Insight as the multi-modal entry point

The unified analysis should not be a terse answer summary — it should make different algorithms diverge from the very first tokens:

INSIGHT
What is the key, non-obvious observation? Why does it turn the original problem into a solvable form?
APPROACH
Which algorithm and data structures? What do the states/variables mean? In what order is it computed?
CORRECTNESS
What is the core invariant? Why are no solutions missed or double-counted?
COMPLEXITY
Time complexity, space complexity.
IMPLEMENTATION CHECKS
Boundary conditions; error-prone details.
FINAL
A complete Python solution in one fixed, consistent format.

This way a problem's four families diverge at the earliest Insight tokens, and the model can more easily keep a multi-modal distribution. Otherwise, plain MLE over four similar long code blobs tends to average into one dominant mode.

Mind the canonical-data risk: the current canonical v1 cannot be used as-is — 3 of the first 12 human-gated items are substantively contradictory. The safer generation flow: ① let the teacher propose candidate insights from the problem alone; ② align insights with verified SE code families; ③ have a critic check insight / algorithm / complexity / code consistency; ④ repair; ⑤ then run code tests plus human semantic spot-checks. Never let the teacher write a long "pseudo-native CoT" while looking at the answer — regen/full already showed that answer-conditioned explanations shorten reasoning and cause capability forgetting.

5.4Adjust the training objective in three phases

Phase 1 — low-risk, immediately doable. Keep the current native-final + final-only setup and change only solution selection:

This separates "family selection" from "reasoning supervision" diagnostically.

Phase 3 — two-stage generation. At inference, do not generate full code immediately:

5.5Data mixture

Do not use SE alone for every bucket:

BUCKET-0SE first — especially strict only-SE rows and genuinely distinct breakthrough families.
BUCKET 1–3Merge SE with BoN/independent, then select by family.
BUCKET 4–15Prefer Base-compatible BoN/loop-0 replay: here the independent solutions actually carry more true algorithm families.
THROUGHOUTKeep 20–30% Base-compatible replay to guard against Dev coverage contraction.

In short: bucket-0 = SE discovery; 1–3 = SE + BoN family union; 4–15 = BoN/loop-0 retention replay.

5.6If GRPO comes later

GRPO must not reward correctness alone, or it too collapses onto a single high-reward mode. At minimum:

R = Rcorrect + λ·Rfamily novelty − β·KL(π ‖ πbase) − γ·Rduplicate

Generate 8–16 candidates per group: passing the full tests earns the correctness reward; belonging to a new family among the group's correct answers earns the novelty reward; same-family duplicates earn nothing extra; the KL term preserves Base's Dev distribution; length and format are constrained.

But I would run family-balanced SFT first: it is cheaper, and it directly answers whether SE's diversity has any training value at all. If even that shows no gain, jumping straight to GRPO would likely just be a more expensive mode collapse.

The decisive experiment Not "K1 vs K4," but K1 vs naive K4 vs genuine family-balanced K≤4 — at equal per-problem weight, equal token/update dose, and identical format. Only that truly answers whether SE's rich solution set can be distilled.
